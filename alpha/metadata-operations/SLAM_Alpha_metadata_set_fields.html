SLAM_Alpha_metadata_set_fields

Overview​

Makes your org's field metadata match a table. Edit the columns you want in SQL, pass the table, and Speediful deploys the changes — hundreds of fields in one deployment, across as many objects as you like.

-- Document and classify a set of fields.
SELECT * INTO dbo.FIELD_EDITS
FROM dbo.METADATA_FIELDS
WHERE sObject = 'Account' AND FieldName LIKE 'Legacy%';

UPDATE dbo.FIELD_EDITS
SET description = 'Migrated from the legacy CRM. Do not use for new records.',
    securityClassification = 'Internal',
    businessStatus = 'DeprecateCandidate';

EXEC dbo.SLAM_Alpha_metadata_set_fields @table = 'FIELD_EDITS';

SELECT sObject, FieldName, SLAM_message FROM dbo.FIELD_EDITS;

Requires the METADATA_DEPLOY entitlement.

The input is a table shaped like SLAM_Alpha_metadata_get_fields's output, and it is updated in place: each row's outcome lands in its SLAM_message column.

The full workflow is in Guide: manage field metadata at scale.

Parameters​

NameTypeDefaultDescription
@tableVARCHAR(256)RequiredA fields table, shaped like get_fields's output. Updated in place — each row's outcome is written to its SLAM_message column, so it must be a writable base table, not a view.
@dry_runBIT01 asks Salesforce to validate the whole deployment and change nothing. Per-row results are still written to SLAM_message.

The input table​

@table needs sObject and FieldName; every other column is optional. Any attribute column present is read, and any cell you have filled in is applied.

The normal way to produce one is get_fields, filtered:

EXEC dbo.SLAM_Alpha_metadata_get_fields @sObjects = 'Account,Contact';

SELECT * INTO dbo.FIELD_EDITS
FROM dbo.METADATA_FIELDS
WHERE description IS NULL;

SELECT * rather than naming columns: it carries the whole shape across, which costs nothing and keeps your edit table comparable to the original.

Wildcards (*) are rejected — set_fields acts on named fields. Naming the same field twice is rejected too (Salesforce API names are unique regardless of case, so it is not clear which row should win, or which row the result belongs on).

What actually gets changed​

A blank cell leaves the org's value alone. To remove an attribute, write !clear

A blank cell means don't touch this attribute — NULL, '', whitespace, and the literal text NULL (which is what SSMS pastes into a worksheet where a cell was empty). Only cells you have actually filled in are applied.

That is what makes a filtered copy of a get_fields table safe to hand over: the columns you did not touch are not "blanked", they are simply not mentioned. But it also means an empty cell can never empty anything — so removing an attribute has to be said out loud:

UPDATE dbo.FIELD_EDITS
SET description = '!clear'          -- removes the description
WHERE FieldName = 'Legacy_Code__c';

!clear is accepted in any writable column, in any case (!CLEAR, !Clear). Clearing something that is already empty is not an error — the row reports No change required., and nothing is deployed for it.

Speediful removes the attribute from the field it redeploys, and because a deployment replaces the whole component, Salesforce drops it. (The sentinel only fits the text columns: length, precision, scale, visibleLines and the BIT columns are typed, so '!clear' will not go into them — and none of them is writable in this release anyway.)

A restore cannot undo a clear it did not record. If a field had no description when you took the snapshot and you have since given it one, handing the snapshot back leaves the new description in place: the snapshot's cell is blank, which means "leave it alone", not "remove it". Put !clear in the snapshot's cell if that is what you want.

Only these columns are applied in this release:

label, description, inlineHelpText, businessOwnerUser, businessOwnerGroup, businessStatus, complianceGroup, securityClassification.

Changing a field's Business Owner​

A Business Owner is a user or a public group, never both — so handing a field from one to the other takes two cells:

UPDATE dbo.FIELD_EDITS
SET businessOwnerGroup = 'Data_Stewards',
    businessOwnerUser  = '!clear';       -- without this, the field would carry both

A blank cell means "leave it alone", so if you name a group and leave businessOwnerUser blank, the field keeps the user it already had — the deployment would carry two owners, and Salesforce refuses it. That is a per-row failure with Salesforce's own message in SLAM_message; Speediful does not second-guess it, here or anywhere else.

A column that is not writable yet is reported, not applied — and does not fail the run​

If length, required, defaultValue or any other reference column differs from the org, the row still deploys the changes it can make, and SLAM_message tells you what was left alone:

Operation Successful. length differs from the org (org: 255, table: 100) and is not writable;
left unchanged.

This is deliberate in both directions. Failing would break restores: a get_fields snapshot carries every reference column, so an admin resizing a field after you took it would turn a routine restore into a failed deployment over a change you never asked for. Staying silent would be worse — you would be told the length = 100 you typed had been applied when it had not.

Changing a field's type abandons the entire run​

A type that differs from the org's deploys nothing

A field's type cannot be changed. More to the point, a type that does not line up almost always means the table's rows are misaligned — a shifted column, the wrong object, a stale copy pasted over a newer one. In that situation the rows that look fine are the dangerous ones, so Speediful deploys none of them:

  • the offending rows report Field type cannot be changed (org: Text, table: Number).
  • every other row reports No deployment was performed.
  • the procedure raises error 88313

Check that your table's rows still name the fields you think they do, and run it again.

Creating fields is not supported yet​

A FieldName your org does not have fails that row with Field does not exist. Creating fields is not yet supported., and the run raises 88313.

A typo must never quietly create a field, so there is no way to opt in to that behaviour today.

Standard and packaged fields​

Standard fields work. securityClassification, complianceGroup, businessStatus and businessOwnerUser deploy on Account.Description exactly as they do on a custom field — these are the attributes Salesforce puts under Field Governance on the field detail page, and they are editable there for standard fields too. An attribute Salesforce refuses on a particular standard field surfaces as that row's error, and only that row's.

Packaged fields are attempted, not predicted. Whether one can be changed is up to the package — managed or unmanaged, locked or unlocked, and whatever its publisher exposed. Speediful sends the change and reports what Salesforce said, row by row. Where Salesforce withholds the field's definition there is nothing to redeploy, and the row fails with Cannot deploy managed component. — the same rule as set_status.

Validate first with @dry_run​

EXEC dbo.SLAM_Alpha_metadata_set_fields @table = 'FIELD_EDITS', @dry_run = 1;

SELECT sObject, FieldName, SLAM_message FROM dbo.FIELD_EDITS;

Salesforce validates the whole deployment and applies none of it. Every per-row error you would have got from a real run is written to SLAM_message, so you can fix the rows it complains about and then run for real. Rows that would have been deployed report Dry run: this change is valid. Nothing was deployed.

Worth doing on a large sweep, because the deployment is all-or-none.

SELECT sObject, FieldName, SLAM_message
FROM dbo.FIELD_EDITS
WHERE SLAM_message <> 'Operation Successful.';

A failed run raises SQL error 88313.

The deployment is all-or-none

Every field in the run goes to Salesforce as one deployment. If Salesforce rejects one of them, every field in that deployment is rolled back — including the ones it accepted. Nothing is left half-applied, and each row's SLAM_message says which it was.

Rows rejected before the deployment (a field that does not exist, an object you cannot see, a withheld packaged field) do not stop the others: they fail on their own, and the rest still deploy.

Setting field metadata REDEPLOYS the field

Salesforce keeps a field's attributes inside the field's definition, and the Metadata API has no operation that changes one attribute on its own. So Speediful retrieves the field, overlays your changes onto exactly what Salesforce sent back, and deploys it again.

Two consequences:

  • Anything changed in the org between the retrieve and the deploy is overwritten. Do not run this alongside a CI pipeline, a change set, an SFDX deploy or a package install — or while an admin is editing the fields involved.
  • Everything Speediful did not touch travels back untouched, including the parts that have no column here: a picklist's values, a lookup's filter, a roll-up summary's criteria. They ride along inside the field's definition.

The deployment carries a bare object file holding only the fields you named, and names those fields individually in the deployment manifest, so nothing else on the object — no other field, no validation rule, list view or layout — is touched.
