SLAM_Alpha_metadata_get_fields

Overview​

Writes the field metadata of the objects you name into a table: one row per field, one column per Salesforce attribute. Description, help text, data sensitivity, compliance categorization, field usage, business owner — everything the field detail page shows you one field at a time, for every field at once.

EXEC dbo.SLAM_Alpha_metadata_get_fields
    @sObjects = 'Account,Contact';

SELECT * FROM dbo.METADATA_FIELDS;

This procedure is read-only. It changes nothing in Salesforce.

Edit the columns you care about in SQL and hand the table to SLAM_Alpha_metadata_set_fields to deploy the changes. The table it writes is also your restore point — hand it back unmodified and the org goes back to what is recorded here.

The full workflow is in Guide: manage field metadata at scale.

Parameters​

NameTypeDefaultDescription
@sObjectsVARCHAR(MAX)RequiredComma-separated object API names, e.g. 'Account,Contact,My_Object__c'. Spaces around the commas are ignored. An object your org does not have is reported on its own row; it does not fail the run.
@tableVARCHAR(256)'METADATA_FIELDS'Destination table for the field metadata.
@exists_actionVARCHAR(20)'fail'Controls the behavior when the destination table already exists.

Valid options:

  • 'drop' - Drop the existing object and create a new one (default)
  • 'rename' - Rename the existing object by appending a timestamp suffix (format: _YYYYMMDDTHHMMSS_MMM)
  • 'fail' - Throws a SQL exception if the destination object already exists
  • 'drop-after' - Like 'drop', but keeps the existing object, renamed, until the run succeeds. See The drop-after option

@exists_action defaults to 'fail' here

Like get_status, and for the same reason: this table is a restore point. If a second get_fields silently overwrote the table holding the values you still have to put back, they would be gone.

There is no all-objects mode. Name the objects explicitly — build the list from SLAM_describe_objects if you want to sweep a whole org:

SELECT STRING_AGG(Name, ',') FROM dbo.DESCRIBE_OBJECTS WHERE custom = 1;

Output table​

Where the org has no value, the cell is empty — not NULL

This is the one Speediful table written that way, and it is deliberate: this table exists to be edited. Filter on = '', not IS NULL.

SELECT sObject, FieldName FROM dbo.METADATA_FIELDS WHERE description = '';

The numeric and true/false columns (length, precision, scale, visibleLines, relationshipOrder, and the BIT columns) cannot hold an empty string, so those stay NULL. They are not writable in this release anyway — and if you are editing this table in a spreadsheet, export it and bring it back with SLAM_table_to_csv and SLAM_Alpha_import_csvs, which is the supported round trip and does not care what the column types were.

What has no column at all — and why nothing is lost

A field's picklist values, lookup filter and roll-up summary criteria are structures, not single values, so no column represents them.

They are not lost. set_fields redeploys the field exactly as Salesforce handed it back, with only your edits overlaid on top — so everything without a column travels through an update untouched. That is also what makes a future Salesforce attribute harmless: an attribute Speediful has never heard of is preserved on deploy, it simply does not appear in the table.

A field's Business Owner is a user or a group — never both

Salesforce sends whichever one the field has, so a group-owned field has businessOwnerGroup filled in and businessOwnerUser empty, and vice versa.

Both are writable, so handing a field from one to the other takes two cells: name the new owner, and !clear the old one.

UPDATE dbo.FIELD_EDITS
SET businessOwnerGroup = 'Data_Stewards',
    businessOwnerUser  = '!clear';       -- without this, the field would carry both

Leaving the other cell blank does not remove it — blank means "leave it alone" — so the deployed field would carry two owners and Salesforce would refuse it. That failure lands in the row's SLAM_message, and only that row's.

precision counts all the digits

The Metadata API's precision is the total number of digits, not the digits to the left of the decimal point that the Salesforce setup UI asks for. A field the UI describes as "16 digits left, 2 right" is precision 18, scale 2.

What is in the table, and what is not​

get_fields reports what the Metadata API returns for the object — which is not the same thing as a list of the fields you can query:

  • Configurable fields only. System fields like Id, CreatedDate or SystemModstamp are not configurable metadata and do not appear.
  • Compound fields appear as the composite. You get BillingAddress, not BillingStreet, BillingCity and the rest.
  • Standard fields are often sparse. Salesforce sends only what has been set on them, so a standard field's row can be almost entirely empty. That is the org's answer, not a gap in the read.

For the complete queryable field list, use SLAM_describe_fields. It answers a different question — "what can I load into?" — from a different Salesforce API.

Custom fields on Task and Event live on Activity

Salesforce keeps them on the shared Activity object. Pass @sObjects = 'Activity' to see them.

Packaged fields are listed too​

Every field is reported, whatever package it came from, tagged with its ManageableState. Hiding them would make the table an incomplete restore point.

Whether a packaged field can be changed is up to the package — set_fields attempts the change and reports what Salesforce said, row by row. If you would rather not go near them, filter them out when you build your edit table:

SELECT * INTO dbo.FIELD_EDITS
FROM dbo.METADATA_FIELDS
WHERE ManageableState IN ('unmanaged', '');   -- yours, and standard fields

Finding the gaps​

The reason most people run this: which fields have no documentation or no governance?

SELECT sObject, FieldName, label, description, securityClassification, businessStatus
FROM dbo.METADATA_FIELDS
WHERE FieldName LIKE '%\_\_c' ESCAPE '\'
  AND (description = '' OR securityClassification = '')
ORDER BY sObject, FieldName;

Empty, not NULL — see the note above.
