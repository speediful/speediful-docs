Guide: suspend automation for a data load

Validation rules, duplicate rules, Apex triggers and flows all run on every record you load. On a large load they are usually what makes it slow, and often what makes it fail: a rule written for a user typing into a page reacts badly to two million rows arriving at once.

This guide is the recipe for turning that automation off, running the load, and putting the org back exactly as you found it.

StepProcedure
1. Record how the org is nowSLAM_Alpha_metadata_get_status
2. Turn off what is in the waySLAM_Alpha_metadata_set_status
3. Load the dataSLAM_load
4. Put the org backSLAM_Alpha_metadata_set_status

Two procedures, working on one table. get_status reads the org's automation into a table; set_status makes the org match whatever a table says. So turning something off is just setting its Active to 0, and putting the org back is handing set_status the original get_status table.

Supported metadata types: ValidationRule, DuplicateRule, ApexTrigger, Flow.

Modifying active state overwrites metadata

Turning a component on or off redeploys it. Speediful deploys the definition it read from the org moments earlier, so anything anyone changed in between — to that component, or to anything else in the same file — is overwritten by what Speediful read.

Salesforce keeps the active flag inside the component's definition, and the Metadata API has no operation that changes one flag on its own. Deploying the component is the only way to flip it, for Speediful or for any other tool.

How much gets overwritten depends on where Salesforce keeps the component:

  • Apex triggers — the trigger's source code is deployed along with its status.
  • Duplicate rules — the whole rule definition is deployed.
  • Validation rules — a validation rule is not a file of its own; it is an element inside its object, so the deployment has to carry an object file. Speediful sends a bare one holding only the rules you named, and names those rules individually in the deployment manifest, so nothing else on the object — no field, list view or compact layout, and no validation rule you did not name — is touched. The rules you did name are still redeployed as Speediful read them.
  • Flows — the exception. A flow is activated through a separate, tiny FlowDefinition component, so the flow itself is never redeployed.

Run these procedures when nothing else is deploying to the org: not alongside a CI pipeline, a change set, an SFDX deploy or a package install, and not while an admin is editing the objects involved.

The recipe​

-- 1. Record how the org is right now. THIS TABLE IS YOUR RESTORE POINT.
EXEC dbo.SLAM_Alpha_metadata_get_status
    @table = 'METADATA_STATUS';

SELECT * FROM dbo.METADATA_STATUS;   -- check this before changing anything

-- 2. Copy out the automation this load has to get past, and switch it off.
SELECT * INTO dbo.METADATA_DISABLE_Account_load
FROM dbo.METADATA_STATUS
WHERE
     (MetadataType = 'ValidationRule' AND FullName IN ('Account.Industry_Required_For_Customer', 'Account.Prevent_Credit_Limit_Below_Zero'))
  OR (MetadataType = 'DuplicateRule'  AND FullName IN ('Account.Standard_Account_Duplicate_Rule'))
  OR (MetadataType = 'ApexTrigger'    AND FullName IN ('AccountTrigger'))
  OR (MetadataType = 'Flow'           AND FullName IN ('Account_BeforeSave'));

UPDATE dbo.METADATA_DISABLE_Account_load SET Active = 0;

EXEC dbo.SLAM_Alpha_metadata_set_status
    @table = 'METADATA_DISABLE_Account_load';

SELECT MetadataType, FullName, SLAM_message
FROM dbo.METADATA_DISABLE_Account_load;   -- every row must say 'Operation Successful.'

-- 3. Run the load.
EXEC dbo.SLAM_load
    @sObject   = 'Account',
    @table     = 'Account_Load',
    @operation = 'insert';

-- 4. Put the org back exactly as it was: hand back the ORIGINAL status table.
EXEC dbo.SLAM_Alpha_metadata_set_status
    @table = 'METADATA_STATUS';

SELECT MetadataType, FullName, Active, SLAM_message
FROM dbo.METADATA_STATUS;                 -- confirm every row succeeded

Get the status first, always​

Run get_status before you switch anything off. It is the only record of how the org looked; without one you are left reconstructing from memory which of those rules were on in the first place. Some of them will have been off already, and turning everything on is not restoring the org — it is changing it.

That is why step 4 hands back the whole METADATA_STATUS table rather than flipping the disable table back to 1. set_status sets an absolute status, so the rules that were off before the load are set back to off, and the ones that were on are set back to on.

Keep the status table until the restore has succeeded

Do not drop or overwrite METADATA_STATUS between steps 1 and 4, and check SLAM_message after step 4. If the restore fails, re-running it against the same table is the recovery path — so the table has to still be there.

This is also why get_status's @exists_action defaults to 'fail': a second get_status cannot quietly overwrite the status you have not put back yet.

Packaged automation is in the list too​

get_status reports every component, including automation that arrived in a package, and tags each row with a ManageableState.

Do not assume packaged means untouchable. Whether a packaged component can be changed is up to the package — managed or unmanaged, locked or unlocked, and whatever its publisher allowed. Any of the four types might be modifiable in one package and read-only in the next, so Speediful does not try to predict it: it attempts the change and reports what happened, row by row.

Some cannot be changed at all — where Salesforce withholds the component's definition, there is nothing to redeploy, and the row reports Cannot deploy managed component. Such a component will run on every row of your load, and no tool can prevent it. If that matters, ask the package publisher whether it honours a bypass setting; many provide one for exactly this.

That is the real reason these rows are in your list. Hiding them would not stop the automation — it would just stop you finding out about it.

Step 2 above names its components explicitly, so nothing packaged gets touched unless you name it. If you would rather rule it out wholesale, add:

  AND ManageableState = 'unmanaged'

Check step 2's results before starting the load. Step 4 (the restore) is unaffected: a packaged component you never changed reports No change required, not an error.

Flows: Active is a version number​

1 does not mean "on" for a flow — it means "version 1"

Salesforce does not switch a flow on; it activates a version of it. So a flow's Active is the version number that is live, and set_status applies it literally:

ActiveWhat it does to a flow
0Switches the flow off
3Activates version 3
1Activates version 1 — not "on"

A blanket UPDATE ... SET Active = 1 over a table containing a flow will therefore roll that flow back to version 1 and make it live.

Switching a flow off by hand is fine (Active = 0 means off for every type). Switching one back on is not: always restore a flow by passing back an unmodified get_status table, which carries the version it was really on. That is exactly what step 4 above does.

For validation rules, duplicate rules and Apex triggers, any positive value just means "on", so SET Active = 1 is safe.

Reading the results​

set_status writes the outcome of each component back into the SLAM_message column of the table it was given, the same way a data load does:

SELECT MetadataType, FullName, Active, SLAM_message
FROM dbo.METADATA_DISABLE_Account_load
WHERE SLAM_message <> 'Operation Successful.';
SLAM_messageMeaning
Operation Successful.The component is now in the status the row asked for
Active state could not be read...The row's Active was NULL, so the component was left alone — see get_status
Metadata not writeable.The deployment failed and Salesforce named no reason for this component
Anything elseThe problem Salesforce reported for that component

If any component fails, SQL raises error 88313 — a failed set_status will not pass silently in an overnight job.

Check step 2's results before you start the load. A row that failed there names automation that is still running.

A failed run can still have changed the org

A run that raises an error has usually still changed the org. Do not read the error as "so nothing happened."

The deployment itself is all-or-none. Everything Speediful sends goes to Salesforce as a single deployment: if Salesforce rejects any part of it, the whole deployment is rolled back and none of it is applied.

But a row can also fail before the deployment — a component that does not exist, one the connected user cannot access, a packaged component whose definition Salesforce withholds. Those rows fail on their own, and everything else is still deployed. SQL throws once the run is over, and the components that deployed stay deployed.

Read SLAM_message to see which is which, rather than assuming the org is untouched.

If the restore fails​

Re-run set_status against the same status table. It is safe to repeat: it sets each component to the status the table records, so running it twice leaves the org where running it once would have.

If it keeps failing, the message on the failing row is Salesforce's own — a component someone deleted while it was off, an object that no longer compiles, a validation rule whose owning object another deployment has since changed. Fix the cause in Salesforce, then run set_status again. Until it succeeds, that automation is still off.

What this guide does not cover​

  • Reading metadata rather than changing it — see SLAM_Alpha_metadata_retrieve, which pulls a component's XML into a queryable SQL Server xml column.
  • Metadata types other than the four above — see SLAM_Alpha_metadata_list, which enumerates components of any type. Only the four automation types have an active status Speediful can set.
