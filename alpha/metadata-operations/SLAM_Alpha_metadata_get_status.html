SLAM_Alpha_metadata_get_status

Overview​

Records the active status of the Salesforce automation that gets in the way of a data load — validation rules, duplicate rules, Apex triggers and flows — into a table.

The table it writes is your restore point. Hand it back to SLAM_Alpha_metadata_set_status and the org goes back to exactly the status recorded here. Take it before you switch anything off.

EXEC dbo.SLAM_Alpha_metadata_get_status
    @table = 'METADATA_STATUS';

SELECT * FROM dbo.METADATA_STATUS;

This procedure is read-only. It changes nothing in Salesforce.

Unlike the other metadata procedures, it takes no input table: it enumerates the org for you. Name the types you want in @types, and filter the output afterwards.

The full workflow is in Guide: suspend automation for a data load.

Parameters​

NameTypeDefaultDescription
@tableVARCHAR(256)'METADATA_STATUS'Destination table for the captured status.
@typesVARCHAR(MAX)'DuplicateRule,ValidationRule,Flow,ApexTrigger'Comma-separated metadata types to read. Spaces around the commas are ignored. Only the four supported types are accepted; any other type fails the procedure.
@exists_actionVARCHAR(20)'fail'Controls the behavior when the destination table already exists.

Valid options:

  • 'drop' - Drop the existing object and create a new one (default)
  • 'rename' - Rename the existing object by appending a timestamp suffix (format: _YYYYMMDDTHHMMSS_MMM)
  • 'fail' - Throws a SQL exception if the destination object already exists
  • 'drop-after' - Like 'drop', but keeps the existing object, renamed, until the run succeeds. See The drop-after option

@exists_action defaults to 'fail' here, and only here

Every other Speediful procedure defaults to your SLAM_Settings.default_exists_action. This one does not, deliberately: a status table is a restore point. If a second get_status silently overwrote the table holding the status you still have to put back, that status would be gone. 'fail' makes the collision loud instead.

ManageableState: packaged components are listed too​

get_status reports every component, including ones that arrived in a package. The ManageableState column tells you which is which:

ValueMeaning
unmanagedYour own — or from an unmanaged package, which is the same thing once installed. Fully editable
installedFrom a managed package. Locked down, but see below
installedEditableFrom a managed package that lets subscribers edit this component
released, betaIn a package this org is developing
deprecated, deprecatedEditable, deletedPackaged and on the way out
"Packaged" does not mean "untouchable"

It is tempting to assume you can only act on unmanaged components. You cannot rely on that in either direction. Whether a packaged component can be changed is up to the package — managed or unmanaged, locked or unlocked, and whatever its publisher chose to expose. Any of the four types might be modifiable in one package and read-only in the next.

That is why Speediful does not filter these rows out, and does not try to predict which are changeable. If it hid them, your status table would be an incomplete restore point: the packaged automation would still fire during your load, and nothing in the table would tell you it was there.

set_status attempts the change and reports what actually happened, row by row. Where a change is not permitted, Salesforce refuses it and its reason lands in SLAM_message. Where Salesforce withholds the component's definition altogether, the status cannot be changed by any tool, and the row says Cannot deploy managed component. — that component will run during your load.

If you would rather leave packaged automation alone, filter it yourself:

SELECT * INTO dbo.METADATA_DISABLE
FROM dbo.METADATA_STATUS
WHERE ManageableState = 'unmanaged';

SnapshotDate is local server time​

SnapshotDate is the local clock of the machine Speediful runs on — your SQL Server host — not UTC, and not the Salesforce org's time zone. It carries no offset, so a value taken either side of a daylight-saving change is ambiguous, and one taken on a server in another region will not line up with a Salesforce audit timestamp.

Every row of a single get_status run carries the same value, so it is a reliable answer to "when was this restore point taken?" — just read it as your server's wall clock. If you need to correlate it with Salesforce's own LastModifiedDate (which is UTC), convert it yourself:

SELECT
    FullName,
    SnapshotDate                                   AS TakenLocal,
    SnapshotDate AT TIME ZONE 'Eastern Standard Time'
                 AT TIME ZONE 'UTC'                AS TakenUtc
FROM dbo.METADATA_STATUS;

Substitute your server's own time zone name. set_status never reads this column — it exists purely so you can tell your restore points apart.

Active for a flow is a version number​

For a flow, 1 does not mean "on" — it means "version 1"

A flow is not switched on; a version of it is activated. So a flow's Active is the version number that is live:

ActiveWhat it means for a flow
0The flow is off (no version is active)
2Version 2 is the active version
5Version 5 is the active version

set_status applies that number literally. If a flow is running on version 5 and you set Active = 1, Speediful will activate version 1 — an old version of your flow goes live.

Always switch a flow back on by passing back a get_status table, unmodified. It carries the version the flow was really on. Hand-editing Active to 1 is only ever safe for the other three types.

For validation rules, duplicate rules and Apex triggers, any value of 1 or more simply means "on", so UPDATE ... SET Active = 1 is fine.

A flow that is switched off records Active = 0, like everything else. NULL is reserved for a status that could not be read at all — see below.

A NULL Active is unknown, not off​

Active = NULL means Speediful could not read that component's status, and SLAM_message says so. get_status enumerates the org itself, so this should not normally happen — a component deleted between the enumeration and the read is the usual cause.

NULL is not the same as 0. set_status skips those rows and leaves the component exactly as it is, rather than guessing — switching off something that may well have been running is the more destructive guess of the two.

SELECT MetadataType, FullName, SLAM_message
FROM dbo.METADATA_STATUS
WHERE Active IS NULL;      -- these will not be set

Always reads the org live​

get_status never serves a component from Speediful's metadata cache. A status read moments after a deployment reflects that deployment. There is no @force_refresh here because there is nothing to force — a restore point built from a stale cache would be a restore point that lies. SLAM_Alpha_metadata_retrieve is the only metadata procedure that caches.
