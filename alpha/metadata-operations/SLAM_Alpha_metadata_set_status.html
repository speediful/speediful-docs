SLAM_Alpha_metadata_set_status

Overview​

Sets each component in a table to the Active status the table gives it. This is how you switch automation off for a data load, and how you put it back afterwards — the same procedure both times.

-- Switch off the automation that would fight the load.
SELECT * INTO dbo.METADATA_DISABLE
FROM dbo.METADATA_STATUS
WHERE FullName LIKE 'Account%';

UPDATE dbo.METADATA_DISABLE SET Active = 0;

EXEC dbo.SLAM_Alpha_metadata_set_status @table = 'METADATA_DISABLE';

-- ... run the load ...

-- Put the org back: hand back the ORIGINAL status table, unmodified.
EXEC dbo.SLAM_Alpha_metadata_set_status @table = 'METADATA_STATUS';

There is no separate "disable" and "enable". Disabling is set Active = 0; restoring is pass back the table SLAM_Alpha_metadata_get_status wrote.

Requires the METADATA_DEPLOY entitlement.

The full workflow is in Guide: suspend automation for a data load.

Parameters​

NameTypeDefaultDescription
@tableVARCHAR(256)RequiredA status table, shaped like get_status's output. Updated in place — each row's outcome is written to its SLAM_message column, so it must be a writable base table, not a view.

The input table​

@table needs three columns; anything else on it is ignored.

ColumnDescription
MetadataTypeValidationRule, DuplicateRule, ApexTrigger or Flow. Any other type fails its row, and the run
FullNameComponent name, e.g. Account.Must_Have_Name
ActiveThe status to set. 0 or less is off; 1 or more is on. For a flow this is the version number — see below

The normal way to produce one is SLAM_Alpha_metadata_get_status, optionally filtered:

EXEC dbo.SLAM_Alpha_metadata_get_status @table = 'METADATA_STATUS';

SELECT * INTO dbo.METADATA_DISABLE
FROM dbo.METADATA_STATUS
WHERE (MetadataType = 'ValidationRule' AND FullName IN ('Account.Must_Have_Name'))
   OR (MetadataType = 'ApexTrigger'    AND FullName IN ('AccountTrigger'));

UPDATE dbo.METADATA_DISABLE SET Active = 0;

SELECT * rather than naming columns: it carries SnapshotDate and SLAM_message across too, which costs nothing and keeps the copy the same shape as the original.

A table with no Active column is rejected. A plain list of components names what to change but not what to change it to, so there is nothing set_status could do with it — run get_status and pass the table it writes.

Wildcards (*) are rejected. set_status acts on named components, so a literal * can never match one.

Setting a flow​

For a flow, Active is a version number. 1 does not mean "on"

A flow is not switched on — a version of it is activated, and Active is that version number. Speediful applies it literally:

ActiveWhat set_status does to a flow
0Switches the flow off
1Activates version 1
5Activates version 5

So if a flow is running on version 5, UPDATE ... SET Active = 1 does not turn it "on" — it rolls your flow back to version 1 and makes that live.

Always switch a flow back on by passing back an unmodified get_status table. It carries the version the flow was really on. Setting Active = 1 by hand is only ever safe for validation rules, duplicate rules and Apex triggers, where any positive number just means "on".

A NULL Active is skipped, not switched off​

A row whose Active is NULL has no status to set. set_status leaves that component exactly as it is and says so in SLAM_message. It does not fail the run.

This is deliberate. NULL means "unknown", and switching a component off on the strength of a NULL would be a guess — one that could stop automation that was running perfectly well. Fix the row rather than relying on it:

SELECT MetadataType, FullName, SLAM_message
FROM dbo.METADATA_STATUS
WHERE Active IS NULL;      -- these were left alone

Packaged components​

set_status will try to set a component that came from a package — it does not refuse anything up front on the strength of its ManageableState.

That is deliberate, because whether a packaged component can be changed is up to the package — managed or unmanaged, locked or unlocked, and whatever its publisher chose to expose. Any of the four types might be modifiable in one package and read-only in the next. Speediful does not try to predict it. It attempts the change and reports what actually happened, row by row.

Where a change is not permitted, Salesforce refuses it and its reason lands in SLAM_message on the row it applies to.

When Salesforce withholds the definition​

Changing a component's status means redeploying it — Salesforce keeps the status inside the component and offers no flag-only operation. Some packages do not give you the component's definition at all: Salesforce hands back the literal text (hidden) in its place. A managed package's Apex source is the case you are most likely to meet.

There is nothing to redeploy, so the status cannot be changed — not by Speediful, and not by any other tool. Such a row fails with Cannot deploy managed component.

Speediful detects this before deploying, and fails only that row. That matters: a deployment is atomic, so attempting it would roll back every other component with it — and you would be told your automation was still on when in fact none of it had been turned off.

A component you cannot turn off will run during your load. If that is a problem, the fix is not in Speediful: ask the package publisher whether the component honours a custom setting or a "bypass" flag, which many packages provide for exactly this reason.

Restoring is unaffected

Restoring hands back the unmodified get_status table, which lists those components at the status they already have. Nothing is being asked to change, so nothing is deployed and the row reports No change required — a restore does not fail just because your org has a package.

If you would rather not go near packaged automation at all, filter it out when you build the table:

SELECT * INTO dbo.METADATA_DISABLE
FROM dbo.METADATA_STATUS
WHERE ManageableState = 'unmanaged';

Setting a status a component already has is not an error​

Switching off something that is already off, or on something that is already on, succeeds and reports 'Operation Successful.'. set_status sets an absolute status; it does not toggle.

That is also why it is safe to run twice. If a run fails half way, the recovery path is to run it again — the components that already landed are simply set to the same status a second time.

Results​

Each row's outcome is written back to SLAM_message on @table:

SLAM_messageMeaningFails the run?
Operation Successful.The component is now in the status the row asked forNo
No change required - already in the requested status.Nothing to deploy. You will see this on a packaged component during a restoreNo
Active state could not be read. Component left unchanged.The row's Active was NULL, so there was nothing to put backNo
Cannot deploy managed component.Salesforce withheld the component's definition, so it cannot be redeployed — see above. It will run during your loadYes
(a Salesforce error)What Salesforce said about this componentYes
Metadata not writeable.The deployment failed and Salesforce gave no specific reason for this componentYes
(anything else)e.g. an unsupported MetadataType, or a component that could not be foundYes
SELECT MetadataType, FullName, Active, SLAM_message
FROM dbo.METADATA_DISABLE
WHERE SLAM_message <> 'Operation Successful.';

Check this before you start your load. A row that failed names automation that is still running.

A failed run raises SQL error 88313.

A failed run can still have changed the org

A run that raises an error has usually still changed the org. Do not read the error as "so nothing happened."

The deployment itself is all-or-none. Everything Speediful sends goes to Salesforce as a single deployment: if Salesforce rejects any part of it, the whole deployment is rolled back and none of it is applied.

But a row can also fail before the deployment — a component that does not exist, one the connected user cannot access, a packaged component whose definition Salesforce withholds. Those rows fail on their own, and everything else is still deployed. SQL throws once the run is over, and the components that deployed stay deployed.

Read SLAM_message to see which is which, rather than assuming the org is untouched.

Modifying active state overwrites metadata

Turning a component on or off redeploys it. Speediful deploys the definition it read from the org moments earlier, so anything anyone changed in between — to that component, or to anything else in the same file — is overwritten by what Speediful read.

Salesforce keeps the active flag inside the component's definition, and the Metadata API has no operation that changes one flag on its own. Deploying the component is the only way to flip it, for Speediful or for any other tool.

How much gets overwritten depends on where Salesforce keeps the component:

  • Apex triggers — the trigger's source code is deployed along with its status.
  • Duplicate rules — the whole rule definition is deployed.
  • Validation rules — a validation rule is not a file of its own; it is an element inside its object, so the deployment has to carry an object file. Speediful sends a bare one holding only the rules you named, and names those rules individually in the deployment manifest, so nothing else on the object — no field, list view or compact layout, and no validation rule you did not name — is touched. The rules you did name are still redeployed as Speediful read them.
  • Flows — the exception. A flow is activated through a separate, tiny FlowDefinition component, so the flow itself is never redeployed.

Run these procedures when nothing else is deploying to the org: not alongside a CI pipeline, a change set, an SFDX deploy or a package install, and not while an admin is editing the objects involved.
