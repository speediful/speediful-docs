Guide: manage field metadata at scale

Salesforce has no bulk editor for field metadata. Descriptions, help text, data sensitivity, compliance categorization, field usage, business owner — they are edited one field at a time, on one field detail page at a time, and an org has thousands of fields.

Two procedures turn that into SQL:

  1. SLAM_Alpha_metadata_get_fields — read the fields of the objects you name into a table.
  2. Edit the table. It is just SQL.
  3. SLAM_Alpha_metadata_set_fields — deploy the table back.

The table get_fields writes is also your restore point: hand it back unmodified and the org returns to the values recorded in it.

Alpha, and it deploys metadata

set_fields changes your org's configuration. Try it in a sandbox first, and read the redeploy warning before running it against production.

A governance sweep, end to end​

1. Read the fields​

EXEC dbo.SLAM_Alpha_metadata_get_fields
    @sObjects = 'Account,Contact,Opportunity',
    @table = 'METADATA_FIELDS';

One row per field, one column per attribute. Keep this table. It is what you will hand back if you want the org as it was.

2. Find the gaps​

Where the org has no value, the cell is empty, not NULL — so filter on = ''. (That is what makes the worksheet round trip below work; see the note on the output table.)

SELECT sObject, FieldName, label, description, securityClassification, businessStatus
FROM dbo.METADATA_FIELDS
WHERE FieldName LIKE '%\_\_c' ESCAPE '\'
  AND (description = '' OR securityClassification = '')
ORDER BY sObject, FieldName;

3. Edit in SQL​

Copy the rows you care about, and fill in the columns you want to change. Everything you leave blank stays exactly as it is in the org; !clear removes an attribute.

SELECT * INTO dbo.FIELD_EDITS
FROM dbo.METADATA_FIELDS
WHERE description = '' AND FieldName LIKE '%\_\_c' ESCAPE '\';

UPDATE dbo.FIELD_EDITS
SET description = 'Documented by the ' + CONVERT(VARCHAR(7), GETDATE(), 120)
                  + ' governance review',
    securityClassification = 'Internal',
    businessStatus = 'Active',
    businessOwnerUser = 'data.steward@example.com';

-- Removing something is explicit — a blank cell would mean "leave it alone".
UPDATE dbo.FIELD_EDITS
SET inlineHelpText = '!clear'
WHERE FieldName IN ('Legacy_Code__c', 'Old_Region__c');

Or join to a spreadsheet your data stewards filled in:

UPDATE e
SET e.description = s.Description,
    e.complianceGroup = s.Compliance_Categories,     -- e.g. 'PII;HIPAA'
    e.securityClassification = s.Sensitivity
FROM dbo.FIELD_EDITS e
JOIN dbo.STEWARD_SPREADSHEET s
  ON s.Object_API_Name = e.sObject AND s.Field_API_Name = e.FieldName;

3b. Or hand the whole thing to your data stewards, in a spreadsheet​

Most governance work is not done in SQL — it is done by the people who know what the fields mean. Export the table, let them fill it in, and bring it back. Two procedures do it:

-- 1. Export. Writes METADATA_FIELDS.csv into the folder you name.
EXEC dbo.SLAM_table_to_csv
    @table_name = 'METADATA_FIELDS',
    @output_dir = 'C:\governance\';

-- 2. ...your stewards open it in Excel, fill in descriptions and classifications,
--    and save it back as CSV...

-- 3. Import. The table is named after the file, plus @suffix: METADATA_FIELDS_EDITED.
EXEC dbo.SLAM_Alpha_import_csvs
    @folder = 'C:\governance\',
    @suffix = '_EDITED';

-- 4. Validate, then deploy.
EXEC dbo.SLAM_Alpha_metadata_set_fields @table = 'METADATA_FIELDS_EDITED', @dry_run = 1;
EXEC dbo.SLAM_Alpha_metadata_set_fields @table = 'METADATA_FIELDS_EDITED';

A round trip you have not edited changes nothing. Empty cells come back as empty cells and mean "leave it alone", and set_fields reads each cell for what it says regardless of the column's SQL type — so it does not matter that the re-imported table types a true/false column as the text True, or a length as 255.0. That is the point of this surface, and it is tested against a real org.

Clearing an attribute is easier here than in SQL

SLAM_Alpha_import_csvs decides each column's type from what is actually in the CSV, so a column your stewards typed !clear into comes back as text — including the numeric and true/false columns, which SQL Server would never have let you put !clear into.

4. Validate​

EXEC dbo.SLAM_Alpha_metadata_set_fields @table = 'FIELD_EDITS', @dry_run = 1;

SELECT sObject, FieldName, SLAM_message
FROM dbo.FIELD_EDITS
WHERE SLAM_message NOT LIKE 'Dry run%';

Salesforce validates the whole deployment and changes nothing. Fix whatever it complains about before you spend a real deployment on it — the deployment is all-or-none, so one bad row rolls back every good one with it.

5. Deploy​

EXEC dbo.SLAM_Alpha_metadata_set_fields @table = 'FIELD_EDITS';

SELECT sObject, FieldName, SLAM_message
FROM dbo.FIELD_EDITS
WHERE SLAM_message <> 'Operation Successful.';

6. Restore, if you need to​

EXEC dbo.SLAM_Alpha_metadata_set_fields @table = 'METADATA_FIELDS';

Only the fields that actually drifted are deployed; everything else reports No change required. and is left alone.

What a plain restore will not undo

A blank cell means "leave the org's value alone", so a restore re-sets what it recorded; it does not remove what you added. If a field had no description before your sweep, handing the snapshot back leaves the description you gave it in place — the snapshot's cell is empty, and empty means "don't touch this".

To take it away, say so:

UPDATE dbo.METADATA_FIELDS
SET description = '!clear'
WHERE description = '' AND sObject = 'Account';   -- fields that had none to begin with

Deploying many fields from a spreadsheet​

The other reason to use these procedures: a migration or consulting project where hundreds of field edits are authored in Excel, not in Setup.

Load the spreadsheet into SQL Server (SLAM_Alpha_import_csvs will do it), join it onto a get_fields table as above, and deploy. One deployment, hundreds of fields, across as many objects as you like — sObject is a column, not a parameter.

Creating new fields is not supported yet. Every row must name a field the org already has; one that does not fails its row. Creating fields from a table is coming in a later release.

Things that will bite you​

A blank cell does not clear an attribute — !clear does. An empty cell, whitespace, NULL, and the literal text NULL all mean leave it alone, because most of a real table is blank and a sweep must not wipe the columns it is not interested in. Removing an attribute is explicit: set the cell to !clear.

"No value" is an empty string in this table, not NULL. Unlike every other Speediful table — this one is meant to be edited in a worksheet, and NULLs do not survive a copy-paste. Filter with = ''.

Only the governance and documentation columns are applied. label, description, inlineHelpText, businessOwnerUser, businessOwnerGroup, businessStatus, complianceGroup, securityClassification. A difference in any other column — length, required, type, … — is reported in SLAM_message and left unchanged. It is not applied, and it does not fail the run.

A field's Business Owner is a user or a group, never both. Handing one over takes two cells: name the new owner, and !clear the old one. Leave the old one blank and the field ends up with two owners, which Salesforce refuses — that row fails, and only that row.

A changed type abandons the whole run. Not one row: the whole run, with nothing deployed. A type that does not match the org almost always means the table's rows have slipped out of alignment, and deploying the other rows of a misaligned table is exactly the disaster worth preventing.

precision counts every digit. The Metadata API's precision is the total number of digits, not the digits left of the decimal point that the Salesforce UI asks for. "16 left, 2 right" is precision 18, scale 2.

get_fields is not a field list. It reports what the Metadata API returns for the object: configurable fields only, and compound fields as the composite (BillingAddress, not BillingStreet). The complete queryable field list is SLAM_describe_fields, which answers a different question from a different API.

Custom fields on Task and Event live on Activity. That is where Salesforce keeps them.

set_fields redeploys the field. Anything changed in the org between Speediful's retrieve and its deploy is overwritten, so do not run it alongside another deployment.

New fields need field-level security before you can load data into them​

Field-level security is not part of a field's metadata definition, so set_fields does not grant it and neither does creating a field in Setup. A field nobody can write to is a field your load cannot populate.

After creating fields (in Setup, or with a future release of these procedures), grant FLS through a permission set or profile. If you forget, SLAM_load's dry run tells you exactly which fields are blocked, and exits with code 9:

EXEC dbo.SLAM_load
    @sObject = 'Account',
    @table = 'Account_Load',
    @operation = 'update',
    @dry_run = 1;
